# 儿童安全桌面 · 鸿蒙端

ArkTS + ArkUI（Stage 模型）实现，对应 `KidsSafeShared/` 里的 MAUI 版本。
平台能力按 `Services/I*.cs` 六个接口一一对应到 `entry/src/main/ets/core/`。

---

## 一、必须先知道的两件事

这两条不是实现取舍，是鸿蒙系统的硬限制。如果和预期不符，越早发现越好。

### 1. 拿不到「设备上装了哪些应用」

枚举全部已安装应用需要 `ohos.permission.GET_BUNDLE_INFO_PRIVILEGED`（system_basic 级），
普通应用申请不到，运行时直接返回 201；`launcherBundleManager.getAllLauncherAbilityInfo`
同样是系统接口。

**所以白名单改成「预设 + 手填包名」**：家长在后台从常见应用里勾，或者自己填
`bundleName` / `abilityName`（包名在「设置 → 应用和元服务 → 应用信息」里能看到）。
不依赖任何特权接口，上架审核也不会因为权限被拒。

### 2. 消费级设备做不到真正的锁定

| 能力 | Windows | Linux（独立会话） | 鸿蒙消费级 | 鸿蒙企业版 |
|---|---|---|---|---|
| 全屏 + 隐藏系统栏 | ✅ | ✅ | ✅ | ✅ |
| 拦返回键 | ✅ | ✅ | ✅（`onBackPress`） | ✅ |
| 禁止 Home / 多任务 | ✅ | ✅ | ❌ | ✅ |
| 禁止下拉控制中心 | ✅ | ✅ | ❌ | ✅ |
| 开机自启、崩溃自动回桌面 | ✅ | ✅ | ❌ | ✅ |

真正的系统级锁定是 `kioskManager`（API 26 / HarmonyOS 7），需要**企业实名认证 +
AGC 申请 `ohos.permission.ENTERPRISE_SET_KIOSK` + 企业签名 Profile + 商用固件**，
个人开发者和普通手机/平板完全用不了。

本工程按 API 12 编译，能覆盖绝大多数在售设备，`Kiosk.ets` 只做沉浸式（全屏、隐藏
状态栏导航栏、常亮、拦返回键）。企业版接入模板放在
`entry/src/main/ets/core/KioskEnterprise.ets.sample`，改名即可启用。

**消费级设备上，产品定位应该是「内容与时长管理」，不是「锁机」。**
想真锁，配华为系统自带的「健康使用设备」比任何第三方应用都彻底。

## 三、编译运行

1. DevEco Studio 5.0 及以上，打开 `Harmony/` 目录（不是上一层）
2. 首次打开会自动同步 `oh-package`，等 hvigor 跑完
3. `File → Project Structure → Signing Configs` 勾选自动签名
4. 连真机（模拟器没有 TTS，也测不出「切后台回来」的行为）后 Run

不打开 IDE 也能编译（工程里没有 `hvigorw` 包装脚本，直接用 DevEco 自带的）：

```sh
export PATH="/d/Program Files/Huawei/DevEco Studio/tools/node:$PATH"
export DEVECO_SDK_HOME="/d/Program Files/Huawei/DevEco Studio/sdk"
node "/d/Program Files/Huawei/DevEco Studio/tools/hvigor/bin/hvigorw.js" assembleHap --no-daemon
```

产物在 `entry/build/default/outputs/default/`。**不加签名配置产出的是未签名 HAP**，
装不进设备；装机请在 DevEco 里勾选自动签名后 Run。命令行构建的用处是快速验证
「代码能不能过 ArkTS 编译器」。

> 如果你想用 HarmonyOS 6 的 SDK，把 `build-profile.json5` 里三处
> `5.0.0(12)` 改成 `6.0.0(20)` 即可，代码不用动。

### 签名：只有 p12 + csr 签不出 HAP

HAP 签名要四样东西，缺一不可：

| 材料 | 怎么来 | 作用 |
|---|---|---|
| keystore `.p12` | DevEco 生成，或 AGC 下载 | 装私钥 |
| `.csr` | 由 keystore 导出 | **只是一份申请**，不是证书 |
| 证书 `.cer` | 把 `.csr` 上传到 AGC「证书管理」后签发 | 证明这个私钥属于你 |
| Profile `.p7b` | AGC 创建，绑定 `bundleName`；调试版还要绑设备 UDID | 规定这个应用能装到哪台设备 |

所以拿到 `xiaojuz.p12`（私钥）+ `xiaojuz.csr`（申请）之后，还差 **`.cer` 和 `.p7b`**。
这两样只能由 AGC 签发，本地任何工具都变不出来——不是配置问题，是流程没走完。

拿到四件套后在 `build-profile.json5` 里填：

```json5
"signingConfigs": [
  {
    "name": "release",
    "type": "HarmonyOS",
    "material": {
      "certpath": "./xiaojuz.cer",
      "storePassword": "******",   // keystore 口令（DevEco 生成的那份是随机的，别丢）
      "keyAlias": "xiaojuz",
      "keyPassword": "******",
      "profile": "./xiaojuz.p7b",
      "signAlg": "SHA256withECDSA",
      "storeFile": "./xiaojuz.p12"
    }
  }
]
```

口令请走环境变量或本机配置，**不要提交到仓库**。没有四件套时，`assembleHap`
产出的是未签名 HAP，只能验证「代码能不能过 ArkTS 编译器」，装不进任何设备。

## 四、和 C# 端的对应关系

| C# | 鸿蒙 | 差异 |
|---|---|---|
| `ISettingsService` + `ChildSettings` | `core/Settings.ets` | 用 `@ObservedV2` 直接驱动 UI，省掉 ViewModel 层 |
| `IScreenTimeService` | `core/ScreenTime.ets` | 只统计本应用在前台的时间；切后台系统挂起计时器 |
| `IAppCatalogService` | `core/AppCatalog.ets` | **能力降级**：不能枚举，改为预设 + 手填 |
| `IAppLauncherService` | `core/AppLauncher.ets` | 显式 Want（bundleName + abilityName） |
| `IKioskService` | `core/Kiosk.ets` | **能力降级**：消费级只能沉浸式 |
| `IStoryService` | `core/StoryService.ets` | 服务端契约完全一致，四个接口一字未改 |
| `Helpers/Tts.cs` | `core/Speech.ets` | 鸿蒙自带离线中文合成，不用装语音包 |
| `Services/StarCenter.cs` | `core/Rewards.ets` | 多加了一张排行榜（C# 端分散在各页） |
| `Services/CareJournal.cs` | `core/Care.ets` | 逻辑一致；`saveMood` 里一并发星，避免「记上了却没星」 |

计时规则有个细节：拉起外部应用时记时间戳，回到本应用时把这段补记进使用时长
（上限 4 小时）。鸿蒙拿不到「别的应用在前台多久」，这是最接近真实的估算方式。

## 五之三、内置游戏《猫国建设者》（Kittens Game）

游戏不是原生重写的——它是一套十几万行的 dojo + React 15 老代码（存档、科研树、
资源产线、季节、外交几十个系统互相咬着），原生化等于重写整个游戏。
所以走的是 **离线包 + Web 组件**：`tools/build-kittens-game.js` 把上游打包成
完全不依赖网络的 `resources/rawfile/playland/kittens/`（约 6.8 MB），
`pages/GamePage.ets` 用 Web 组件装进去。

```sh
node tools/build-kittens-game.js          # 默认源目录 D:/迅雷下载/cat-zh-main
node tools/build-kittens-game.js <源目录>  # 源目录换地方时显式传
```

打包时做了这些改动（游戏逻辑一行没改）：

| 问题 | 原因 | 做法 |
|---|---|---|
| 断网白屏 | React/jQuery/dojo/lz-string/SystemJS 全从 CDN 拉 | 换成 `lib/` 本地副本 |
| 模块加载失败 | `System.import()` 走 XHR，`resource://rawfile/` 下被拦 | 换成一模一样的 `<script>` 注入加载器（仍保持顺序） |
| 语言包加载失败 | `$.getJSON('res/i18n/zh.json')` 也是 XHR | JSON 内联进 `offline.js`，这两个 API 改成读内存 |
| 游戏时间不走 | blob Worker 在本地源下可能被拦 | 关掉 Worker，退化成 `setTimeout` 计时 |
| 数据上报 | 百度统计 / GA / `server.json` 里的 telemetryUrl | 全部删除 |
| 右侧被裁 | `body` 与 `#gamePageContainer` 写死 1300px、`#game` 写死 1180px + `nowrap` | `res/mobile.css` 在 ≤900px 时压回屏幕宽并改单列 |
| 孩子能删档 | 顶栏有 Reset / Wipe / DEV 作弊面板 / 站外链接 | `res/kidsafe.css` + `kiosk-guard.js` 双保险（CSS 藏、JS 擦并拦跳转） |

`kidsafe.css` 不带媒体查询，**任何屏宽都生效**（平板横屏也看不到删档按钮）；
`mobile.css` 只管布局。两者分开放，改布局时不会不小心把安全层带掉。

存档在 Web 组件的 localStorage 里（`domStorageAccess(true)`），游戏本身每 400 tick
自动存一次，等于约 80 秒一次，所以顶栏的「保存」被藏掉也不会丢档。

> 已知取舍：游戏原生的「选项」面板（主题、字号）也一并藏了。恢复办法是从
> `kidsafe.css` 的 `.links-block` 选择器里去掉对应项。

`$rawfile()` 的参数必须是**编译期字面量**，传变量过不了编译，所以入口写成 `if/else`

### 中国象棋：复用工程素材，规则与 AI 自己写

工程文件只提供**美术与音效**，`Engine/`、`SuanFa/` 是 C# 的，没法直接搬，所以规则重写：

- 棋盘几何是**量出来的**，不是猜的。`board.png` 767×842，交叉点从 (110, 96) 起、
  步长 67.5；棋子按 `STEP × 0.87` 定尺寸，用百分比定位，换任何屏宽都跟着棋盘缩放。
- 将军判定不生成对方所有走法（那样每步都要遍历 16 个棋子 × 全盘），而是**从帅/将反向发射线**：
  沿四条直线查车/炮/对面的将（照面），再查马腿、象眼、过河兵。一步判定的开销从「全盘生成」
  降到「几条射线」，AI 才能在同一时间预算里多搜两层。
- 走子分两步：`pseudoMoves()` 出伪合法着法，再走一步试 `isChecked()` 过滤自杀。
  将帅照面靠反向射线里的「对面是将」这一条兜住，不用单独写规则。
- AI 是**迭代加深 + 时间预算**，不是固定深度：
  `maxDepth = [0, 2, 3, 4]`、`budget = [0, 100, 500, 1400] ms`（第 0 档是双人，不跑 AI）。
  固定深度 2 会走出来「送马」的棋——深度 2 看不到对方吃子后的反吃，加深一层才正常。
- 规则用 **perft** 做回归：初始局面 `perft(2) = 1920`、`perft(3) = 79666`，
  这两个是象棋界的标准值，对上了说明走子生成没有漏或多。
- 界面：顶部 人机/双人 + 难度，底部 悔棋 / 重新开始。悔棋按**两步**回退（连电脑那一步一起退），
  否则人机模式下点一次悔棋等于没动。被吃掉的棋子从 `history` 反推，不是单独记账，
  所以悔棋、重开之后吃子栏永远是对的。
- **尺寸自适应踩过一次坑**：原来只在 `window.resize` 和 `ResizeObserver` 里调 `layout()`。
  WebView 刚加载时盒子往往还没被摆到最终大小，`layout()` 按一个偏小的盒子算完就再没人叫它，
  棋盘于是永远停在「八成宽、上下各空一大片」。
  现在做三层兜底：启动时 `layout()` + 双 `requestAnimationFrame`、`load` 与 `fonts.ready` 各重排一次，
  再加「6 秒内每 400ms 比一次盒子，变了就重排」的收尾轮询。同时观察 `#stage` 和 `#boardArea`
  （规则面板高度会反过来影响棋盘可用高度）。
- **上下空白不浪费**：棋盘按满宽撑开后，剩下的高度给「红方吃 / 黑方吃」和一块**象棋走法说明**
  （车马炮相士将兵 + 赢法，共 8 条），标题栏可点收起。规则面板高度由 JS 定：先算「棋盘满宽要多高」，
  剩下的才给规则，挤不出来也至少留 18%；放不下时 `#rulesBody` 自己滚，底部用 sticky 渐隐提示「还有更多」。
  横屏改成「棋盘在左、吃子+规则在右」，否则竖着堆会把棋盘压成一条。
- 这一套判断写进了 `tools/test-layout.js`（棋盘 ≥ 92% 宽、不变形、居中、8 条规则、不压底栏、页面不溢出）。

### 五子棋：只搬算法，界面重写

`D:/Downloads/Gomoku-master` 是个纯前端小工程（`index.html` + `css/style.css` + `js/main.js`），
棋盘写死 450×450、结算用 `window.alert`、没有重开也没有悔棋。所以**算法搬过来，界面重写**：

- 原工程的核心是**赢法数组**：开局先把全盘 572 种「五连」枚举出来编号，
  每个交叉点记下自己属于哪几种；落子时只给经过这点的编号计数，
  判断胜负和 AI 打分都变成查表，不用每次扫全盘。这套结构原样保留（`buildWins()`）。
- AI 权重也沿用：自己成四 20000、堵对方成四 10000，所以「能赢就先赢」。
  修了原版一个选择逻辑的问题（`max` 在玩家分和电脑分之间共用，会漏掉更该堵的点），
  改成每个候选点算 `atk + def × 权重` 再排序，同分优先靠中路。
- 悔棋要求计数能撤销，而原版的 `myWin[k]++` 是增量记账、退不回去。
  改成**从棋谱整盘重算**（225 × 572 的查表，毫秒级），顺带解决了「同一条线上黑白都有」
  的死线标记（记成 6）。
- 界面：15×15 木纹棋盘用 Canvas 画，`min(宽,高)` 自适应；最后一手加圆环，五连画红线；
  `alert` 换成页面内结算；人机/双人、三档难度、悔棋。

### 数独挑战：本地生成，唯一解校验

- **不留题库**：题库小了玩腻，大了占体积。直接算——先随机回溯填满一个合法终盘，
  再随机挖洞，**每挖一个就验一次唯一解**，不唯一就填回去。
  困难档挖到 27 个给定数，整题生成通常不到 1 毫秒（Chrome 里测 `Date.now()` 都是 0）。
- 唯一解用**位掩码 + MRV**（每次挑候选最少的空格）的回溯，数到 2 个解就提前返回。
  挖洞最坏要跑 81 次校验，慢机器上加了个 900ms 预算，超时就带着当前题面收工（只是给定数多一点）。
- 候选数用**位掩码**存（第 n 位代表数字 n），省掉一堆数组增删。
- 提示只给 3 次，填错会记失误但不判负——对小孩来说「一步错就重开」太劝退。
- 完成时间按难度存 localStorage，破纪录会在结算里提示。

### 2048：配色照参考图，滑动 + 撤销

- 配色全部取样自参考图：米白底 `#FBFAF5`、金褐标题 `#E2C08C`、实心按钮 `#E4C68F` + 白字。
  数字块按指数做成同一族金色（2 最浅 → 2048 深棕），128 以上换白字。
- 移动逻辑：每条线按「朝移动方向的那条边」排好序再压缩合并，**一块只合一次**；
  合并的块先跟着目标格做位移动画，90ms 后删除并放大一下，新块再弹出来。
- 撤销保留 3 次，快照存的是**移动前**的数值棋盘（这点踩过坑：一开始在移动后取快照，
  等于什么都没存）。
- 4×4 目标是 2048，5×5 是 4096；达成后可以「继续玩」。排行榜取每档前 5 名存 localStorage。
- 两个坑写在代码注释里：合并时「我吃掉了谁（absorb）」和「我被吃掉了（eaten）」必须分开标，
  混用一个标记会把合并结果直接从棋盘里过滤掉；方向序列在向右/向下时要倒序。

### 植物大战僵尸：横屏 + 9×5 草坪 + 阳光经济

- **横屏**：竖屏时把整个 `#app` 用 `translate(w,0) rotate(90deg)` 转 90°，尺寸按横屏逻辑设置。
  这样手机竖着拿也能玩（画面是横的，转一下手机就正了），转到横屏时 `#app.rot` 自动失效。
  旋转后屏幕坐标和元素局部坐标**互换了轴**，点格子必须换算：
  `u = (clientY - rect.top) / rect.height`、`v = (rect.right - clientX) / rect.width`，
  不换算的话点第 1 格会种到第 9 格。
- 草坪不再按 `lawn.jpg` 的 746×513 定比例（那个比例在横屏里只填得满中间一条，
  上下两大片空绿），改成**优先铺满**，只约束单格宽高比 `q = clamp(宽×行/(列×高), 0.85, 1.7)`，
  免得植物被拉成一张饼。
- 底图 `lawn.jpg` **裁成只剩草地**——原图带砖墙和围栏，直接铺会把第一列挤掉。
  砖墙单独做成 `#board`（占宽 8%），实体坐标系 `#lawn` 从 8% 起，两者分开，
  植物和僵尸的百分比坐标才和格子对得上。
- 割草机素材包里没有，手绘成 `img/mower.svg`。停位 `MOWER_X = -0.038`，
  在草地左边界**外面**，视觉上贴着墙脚，不占第一列格子。
- 五种植物（向日葵 50 / 豌豆 100 / 坚果 50 / 寒冰 175 / 樱桃 150）、四种僵尸
  （普通 200 / 路障 420 / 铁桶 700 / 旗帜 220），阳光 11 秒产一次，冷却按秒走。
- 波次表写死 10 波：`[1,1,2,2,2,3,3,4,4,5]`，首波 9 秒，之后每 12 秒一波（共 27 只），
  第 5、10 波是旗帜波。生成用了 `setTimeout(idx*700)` 让同一波错开走上来，
  不然一屏同时冒出来太突然。
- 坚果墙按血量切换裂纹贴图，寒冰减速、樱桃范围爆炸、割草机一次性清一整行。
- **「看不到僵尸」的坑（线上真实反馈）**：波次调度里的 `setTimeout` 回调写了
  `if (myGen === gen)`，`myGen` 其实是 `reset()` 的局部变量，在 `runSchedule` 作用域里
  根本不存在；`'use strict'` 下读未声明变量直接抛 `ReferenceError`，**回调整段不执行**。
  现象极具迷惑性：波次提示照常滚动（第 4/10 波）、阳光照常掉、就是没有僵尸。
  修法是把本局的「身份证」（`gen` 和 `state` 引用）闭包进回调再校验：
  ```js
  var st = state, g = gen;
  setTimeout(function () { if (g !== gen || state !== st || st.over) return; spawnZombie(k, r); }, idx * 700);
  ```
  顺带修了胜利判定：原来只看 `schedule.done && 场上无僵尸`，而最后一波标记完成后还有
  0.7s×N 的生成窗口，那一瞬间场上也是空的 → 会直接判通关。改成
  `state.spawned >= state.total && !state.zombies.length`，给 `state` 加了 `spawned` 计数。
- 操作提示改成浮在草坪下沿的小胶囊、8 秒自动淡出——横屏里一行提示条太贵了。
- **阳光必须是正方形**：`.sun` 原来写 `width:13%; height:13%`，草坪固定 1.45 比例时还行，
  改成铺满之后草坪变成 3:1，阳光就被拉成一颗扁椭圆（截图里特别明显）。
  现在尺寸由 `layout()` 按草坪高度算成同一个 px 值（`--sun` 变量，约 15% 行高，最小 28px）。
  左上角的阳光计数胶囊同理：给了固定 28px 高度 + 14px 圆角，不再是「图标高度 + 2px padding
  套 `radius:999px`」压出来的扁片。

### 蛇蛇方块：纯 Canvas，无素材依赖

- 逻辑世界固定 480×800，canvas 铺满屏幕后**整体缩放居中**：
  ```js
  scale = Math.min(aw / W, ah / H);
  offX = (aw - W * scale) / 2;  offY = (ah - H * scale) / 2;
  ```
  这样长屏短屏都不出黑边、不裁切（第一版让 canvas 跟着容器变尺寸，结果世界被切掉一截）。
- 8 条车道，拖动控制（也支持方向键）。
- 障碍方块上带数字，撞上**长度减 N**（不是直接死），长度归零才结束——给容错空间。
- `spawnRow()` 保证每排**至少留两条连续空车道**，随机生成也不会生成出必死的一排。
- **修过一个「吃小白球整条蛇消失」的 bug**：`drawSnake()` 从蛇尾往蛇头画，越界时用了
  `break`——长度一旦超过 10，尾巴第一轮就越界，`break` 把整条蛇全跳过了，
  画面上一个金色像素都没有（顶栏长度还在涨，看着就像「吃了球，蛇没了」）。
  改成 `continue` 只跳过越界的那几颗。顺手把球间距改成**自适应**：
  `avail / (len - 1)` 再夹在 13~24px，长度增长时整条蛇会挤紧但一直看得见；
  吃球还加了「+2」飘字和长度数字跳动。

所以全部重画成手绘 SVG，由 `tools/build-baobei-cartoon.py` 生成，一条命令重跑：

| 文件 | 内容 | 尺寸 |
|---|---|---|
| `kid.svg` | 小男孩，5 帧走路 | 460×128（每帧 92×128） |
| `foe1..4.svg` | 四个陌生人：鸭舌帽墨镜 / 假医生 / 保安帽 / 连帽衫 | 同上 |

**体积**：19 张位图合计约 800 KB → 13 个 SVG 共 113 KB，而且放大到平板不糊。

几个必须写下来的约束（改图前先看）：

1. **每一帧必须正好等宽**。走路动画是 `<img>` 上一句 `translateX(-帧号 × 20%)`，
   百分比是相对整张图的宽度算的 —— 5 帧不等宽，第 3 帧之后就会错位、露出半张脸。
   所以生成器里帧宽写死 `FRAME_W = 92`，总宽 = 5 × 92。
2. **手臂的肩点要在身体轮廓外面**。第一版肩点放在 x=31/61，而身体是 x=30..62，
   整条胳膊被身体盖住，五个人物看起来都像「麻袋」。改成 27/65 才露出来。
3. **手臂和身体同色会糊成一块**。即使露出来了，同色也只看到一条外轮廓。
   袖子统一压暗 14%（`shade(shirt, 0.86)`）才分得开。
4. **帽檐不能压到眼睛**。鸭舌帽第一版画到 y=36（眼睛在 37），人物全成了「蒙面人」，
   孩子分不清表情。抬到 y=29，只压眉毛。
5. **兜帽要画成「环」不是「圆」**。整块圆直接把脸盖成黑团；
   用 `fill-rule="evenodd"` 画内外两个圆，脸才框在中间，再补一撮露出来的刘海。
6. **竖屏只看得到画面中间 26%**。场景背景是 `center/cover`，390×844 的手机上
   1024×576 的图被裁到 x 380..645 —— 第一版把熊猫放在 210 / 810，手机上打开是一片空草地。
   主角必须压中轴（现在是 430 / 600），两侧只放竹林当氛围。

**顺手修掉的一个老 bug**：原工程 `win.png` 画的是「坏人把小孩带走」，`lose.png` 才是
「警察救下孩子」，而代码是 `win ? win.png : lose.png` —— 也就是说**通关反而看到孩子被拐走**。
重绘时按语义重新出图（`win.svg` = 警察护住孩子），这个错位就自然消失了。

**地图还有一个真问题**：标记是按屏幕百分比定位的（`SCENES.at`），背景图是 `object-fit: cover`。
竖屏下 4:3 的图被裁掉两侧，建筑根本不在屏幕上，而「动物园」的牌子照旧飘在 20%/30% 的位置 ——
牌子浮在空草地上，点进去却是对的。改成「舞台」：`fitMap()` 按图片比例算出舞台尺寸并居中，
标记挂到舞台里、按百分比定位，两头就永远对得上（`index.html` 的 `.mapStage`）。

## 五之六、24 点：分数运算 + 穷举出题

四张牌用 + − × ÷ 凑 24，每张用一次。看起来简单，坑都在数值上：

- **必须用分数，不能用浮点**。`3 8 3 8` 的唯一解是 `8 ÷ (3 − 8÷3)`，浮点算出来是
  `23.999999999999996` —— 孩子算对了反而不给过。所以内部全是 `{n, d}` 并随时约分，
  判定写成 `d === 1 && n === 24`。
- **出题要保证有解**。随机 4 张牌里大约三分之一无解，直接发牌会出现「这题根本做不出来」。
  出题器先穷举（四张牌的所有合并顺序约 7680 种，毫秒级），有解才发。
- **难度靠解法数量分**。简单档要求 ≥3 种解法（1–9 的牌），挑战档要求 ≤2 种（1–13）。
  第一版循环 4000 次找牌，挑战档偶尔会转两秒；改成 400 次 + 兜底「第一副有解的」。
- **提示要从当前牌面重算**。第一版直接展示原答案的第一步，但孩子往往已经自己合了一张，
  提示就会指向两张已经不在的牌。现在每次都用 `firstStep()` 从当前四张牌重新找下一步，
  并把那两张牌高亮。
- **撤销存的是牌堆快照**，不是操作日志。合并会把两张牌标 `dead` 再 push 一张新牌，
  回滚快照比反算简单可靠。

星星：一次做出来 2 颗，用过提示 1 颗，换题不给。成绩记「本次已解几题」。

**踩过一次 ArkWeb 的渲染坑（真机上才复现）**：卡片原来写了 `border-radius: 22px` + `overflow: hidden`。
Chrome 上一切正常，鸿蒙上四张牌**只有被选中的那张画得出数字**，其余三张是白板，
屏幕上还多出一条贯穿的斜线 —— 那是圆角裁剪掩码退化后的边。
原因是被选中那张带 `transform: translateY(-3px)`，单独成了合成层，所以它躲过了这个渲染缺陷。
修法不是加 hack，而是**根本不需要裁剪**：数字是唯一的子元素，靠字号分档（`w3` / `w4` 类）
保证三位数、四位数也不出框，`overflow` 干脆去掉。
`tools/test-layout.js` 现在会断言「卡片的 computed overflow 必须是 visible」，防止有人手滑加回去。

> 这条经验适用于所有 H5 游戏：**圆角 + `overflow:hidden` + 里面装文字**，在 ArkWeb 上不可靠。
> 裁剪只留给 canvas 容器或纯色块，文字容器一律靠布局与字号自适应。

**上报链路**（`GamePage.ets`）：

```
H5  →  window.KidsSafe.award(key, stars, score, sub)
        ↕ javaScriptProxy
     AwardBridge.award()  →  rewards.grant()
```

- H5 侧一律包在 `try { } catch (e) {}` 里：电脑上直接用浏览器打开时没有桥，
  不包的话异常会打断结算逻辑，游戏就卡在结算页。
- ArkTS 侧**强制把 key 改成本页的 `gameKey`**：万一某个游戏抄了别人的上报代码，
  星星也只会落在「正在玩的这个游戏」上，不会串榜。
- 猫国没有「结束」这个时刻（增量游戏），由 `GamePage` 每 5 分钟代发一次。
- 上报成功弹一个「⭐ +3」浮层（不是 toast）：不打断操作，也不会盖住游戏自己的结算卡。

**知识类怎么算「完成」**：古诗 / 口诀 / 安全 / 故事四个详情页各加了一个按钮
（「我背会了」「我念会了」「我记住了」「我读完了」）。为什么不是自动判读完 ——
朗读有没有真的听完、文章有没有滑到底，都判不准；而「按下按钮」是孩子明确表达
「我学会了」的动作，也顺带让星星发得有理有据。**只有第一次给星**，否则孩子会把按钮
当老虎机按。

**商店**：商品完全由家长配置（上架 / 价格 / 备注 / 删除）。默认给了四件零成本奖励
（看动画片 20 分钟、挑一本绘本、点一道菜、周末去公园），家长不配置也不至于「星星没处花」。

> 六条教训：
> 1. 断言写**不变量**，不写快照。象棋「场上仍 32 子」第一版直接失败——黑炮合法吃了个马。
>    正确写法是「场上 + 被吃 = 32」。
> 2. 别把「值等于某个中间态」写死。PvZ 割草机断言写 `mowers[r] === 1` 失败了，
>    实际是割草机已经冲出去变成 `2`——写成 `>= 1` 才对。
> 3. **时间轴相关的逻辑，必须先确认测试真的把时间推进了**。无头 Chrome 里
>    `requestAnimationFrame` 基本不跑，`--virtual-time-budget=4000` 下 `state.t` 一直是 0，
>    所以「巡检 0 报错」其实什么也没测到。PvZ 的 `myGen` 崩在 t=9s 的定时器里，
>    就是被这个盲区漏过去的。后来改成用 `setInterval` 手动每 12ms 调一次 `step(0.05)`，
>    一口气把 t 推到 58 秒，才把「波次推进了但僵尸为 0」照出来。
> 4. **「我这边客户端连得上」不等于「真客户端连得上」**。家长端服务第一版是用脚本模拟
>    孩子端测的，全绿；但把那台「孩子端」换成真页面之后才发现，台词是逐字打出来的，
>    脚本一看到有字就去比对，比到的是「小朋友，我」半句。
>    断言要等**该稳定的东西稳定**之后再比，而不是等「第一个非空值」。
> 5. **别指望 CDP 帮你把返回值带回来**。`Runtime.evaluate({awaitPromise: true})`
>    在这套环境里永远拿到 `undefined`，`awaitPromise` 形同虚设。改成页面自己写
>    `window.__RESULT`、外面轮询去取，对「脚本跑多久」完全不敏感，比等返回值稳。
>    顺带两条：注入脚本要包成函数再调（直接写 `window.__run = (async()=>{...})()`
>    会在页面加载时立刻执行，等 CDP 去调时它已经是 `Promise` 不是函数）；
>    对象字面量里 getter 和同名方法互相覆盖，`get skip()` 会被下面的 `skip()`
>    悄悄盖成函数，断言打印出来是一整段源码 —— 改名 `get skipCount()`。
> 6. **等图片加载再量尺寸**。病毒斗士首轮 6 项 FAIL 全是假失败：`fit()` 挂在图片
>    `onload` 里，断言跑得比解码快，canvas 还停在内核默认的 300×150。
>    测试开头先轮询 `while (!side && tries < 120) await 50ms`。

## 五之八、学习天地与安全问答：题库移植 + 判分

对应 C# 的 `LearnWorldPage` / `OralPracticePage` / `ExamPage` / `SafetyQuizGamePage`。
四个页面、两套题库，全部离线。

### 为什么口算和模拟考挤在一个入口

桌面上已经有 15 个磁贴，再拆两格会挤到第二屏；而「练口算」和「做卷子」本来就是
同一件事的两个强度，共用一张年级表反而更好理解：先选年级，再选模式。
模拟考没有 1~2 年级的卷子（题库从三年级起），这两格直接标灰写「暂无模拟卷」，
而不是让家长点进去看一个空列表。

### 口算：一~四年级现场出题，五~九年级查题库

一~四年级是纯四则，题目空间足够大（一年级光「20 以内加法」就有 190 种），
现场出题可以做到**每次练都不重复**；题库反而会越练越熟，练到最后是在背题。

五~九年级不行：题型发散到小数乘除、分数、解方程、根式、几何、统计，
现场生成很容易出「1 ÷ 3 = ?」这种没法用数字键盘答的题。所以这五级用整好的
368 道固定题（`data/MathBank.ets`）。

题库有个坑：**边缘格子的题很少**。初三「除法」只有 4 道，初二 5 道。
原样抽的话孩子会看到「共 4 题」的残缺一轮，所以抽不满时按轮次重洗再抽
（`generateOral` 里的 while 循环），保证每轮都是 10 道，且两次抽到同一题不会挨在一起。

星星：全对 5 颗、八成以上 4 颗、及格 2 颗、其余 1 颗。「来做就有收获，但全对值得多给」。

### 模拟考：答一题不报对错，交卷才批改

和口算刻意相反。考试场景要保留检查的余地 —— 边做边判会让孩子靠反馈试答案，
而不是真的算。所以可以前后翻、可以改答案，最后统一交卷。

- 三种题型一套翻页：单选给 A~D、判断给对/错、填空给输入框；
- 判断题的「对 / 错」不建在库里，由界面生成，库里只存答案 —— 加题型不用改数据；
- 漏答点交卷会先提醒一次「还有 N 道空着，再点一次就交卷」，第二次才真交；
- 交卷后给百分制分数 + 逐题解析（对错都显示题干、你的答案、正确答案、解析）。

判分（`core/ExamGrade.ets`）是这套东西里最不能错的一段：**孩子答对被判错，比不判分更伤人**。
所以它吃下了几乎所有的书写习惯差异：

| 输入差异 | 处理 |
|---|---|
| 全角数字、全角括号（中文输入法默认） | 全角 `FF01`~`FF5E` 转半角 |
| 前后空格、全角空格 | 直接丢 |
| 句末多余的句号 | 去尾部的 `.`（小数中间的 `.` 不动） |
| `−` `–` `—` `－` 四种减号 | 统一成 ASCII `-` |
| 英文大小写（`beijing` / `Beijing`） | 转小写 |
| `0.5` / `0.50` / `.5` | 数值相等即算对（差 < 1e-6） |
| 填空多写法（`丑陋\|难看`） | `\|` 分隔，命中任一即算对 |
| 引号（`「」""''`） | 一律不算内容 |

反过来，判分只回答「对不对」，不猜意图：空答案、超范围字母一律算错。

### 安全问答：40 题抽 8，选项打乱

和「安全知识」是同一主题的两种形态：那边是读的贴士，这边是答的题，
分类名刻意保持一致（交通 / 防拐 / 防火 / 用电 / 溺水 / 饮食 / 灾害 / 网络 / 急救 / 自我保护）。

- 每轮从 40 题里抽 8 道，**每题选项也打乱** —— 不打乱的话孩子记的是「第三题选 B」；
- 每题只有一次机会（再点别的选项不生效），避免「挨个试」；
- 答完立刻给解析，**答错也给**：错题不解释，孩子只会记住「这题我错了」。

### 移植这道题踩到的四个坑

1. **SQL 有多条 INSERT，只取第一条**。题库是一套卷一条 `INSERT`（21 条），
   第一版只解析了第一条，输出「1 套卷 12 题」，看起来还挺像对的。
   改成扫全部 `INSERT INTO <table> ... VALUES` 才对。
2. **安全题库按 `new() {` 切块，会把选项数组切走**。选项本身也是
   `Options = new() { ... }`，按这个切分，每道题都只剩题干、选项全空 —— 而且不报错。
   改成一条完整正则（题库字段顺序是全仓库统一的），并用 `CorrectIndex` 出现次数核对总数。
3. **`spokenOf` 在 C# 端就有 bug**：`prev` 只在运算符分支里更新，数字后面 `continue`
   跳过了，所以「5 - 2」会被念成「五负二」。移植时把 `prev` 跟着数字走修掉了
   （原来的「减 / 负」判据是对的，只是拿到的 `prev` 永远是空格）。
4. **`6x² ÷ 2x = ?x` 这类题不能当系数题算**。写自检脚本时先把 x 抹掉当系数，
   算出 18（正确是 3x）。这类带次方的直接跳过，别硬算。

## 五之九、关怀中心：情绪出口

这一块在 C# 端是完整的一套（`CareCenterPage` / `MoodJournalPage` / `CareLessonPage` /
`BreathingPage` / `LetterToParentsPage` + `CareData.cs` 约 35KB 内容），鸿蒙端整组搬了过来。

它不是「学习」也不是「游戏」，做的是另一件事：**孩子心里堵的时候，有个地方可去**。
所以它的一堆设计取舍都和平时的功能相反 —— 下面几条值得记住，改代码前先看一眼。

### 五个页面

| 页面 | 做什么 | 入口 |
|---|---|---|
| 关怀中心 | 点一个表情记今天的心情、随机暖心话（可朗读）、五个功能入口、求助热线 | 桌面磁贴 💗 |
| 心情日记 | 14 天趋势柱、记了几天 / 连续 / 最常出现、全部记录 | 关怀中心 |
| 心理小课堂 | 20 节（给孩子 10 / 给家长 10），分两套配色 | 关怀中心 / 家长后台 |
| 呼吸放松 | 4-7-8 呼吸，圆圈随阶段缩放，4 轮约 1 分半 | 关怀中心 |
| 想对爸妈说 | 6 个开头提示、写一句、朗读、存本机 | 关怀中心 |

家长后台里另有一张「心理关怀」卡：显示「最近 7 天孩子记了几天心情」，
加一个「给家长的心理课」入口（直接定位到家长那 10 节）。**只给天数，不给内容。**

### 六个刻意的取舍

1. **不自动帮孩子判断「该求助」**。心情日记里只有一条会多说一句的情况：
   「想人」「难过」累计出现 3 次以上，才提示「试试呼吸放松，或者打 12355」。
   其余一律只写事实（「最近 14 天你记录了 8 天」），**不写「你很乐观」「你最近很消极」**。
   评价会让孩子开始表演给系统看，这个功能就废了。

2. **今天没记心情，连续天数不清零**。`streak()` 从昨天往前数。
   否则孩子早上一打开就看到「0 天」，会觉得昨天白记了 —— 反而更容易放弃。

3. **先记录，再问要不要补一句话**。C# 端是点完表情弹输入框问「想多说一句吗」，
   鸿蒙端改成：心情立刻落盘、星星立刻到账，然后在卡片里展开一行输入。
   区别在于「我记完了」这件事不被弹窗打断 —— 不愿说的孩子可以直接走开。

4. **同一天重记不发星**。早上记「开心」，下午想改成「想人」，改一次就给一颗星，
   孩子会把它当老虎机。心情的星星一天一颗，改多少次都一样。

5. **拨号拉起系统拨号盘，不直接外拨**。直接拨要 `ohos.permission.PLACE_CALL`
   （普通应用拿不到），而且孩子误触就拨出去也不合适 —— 让他自己按最后那下绿色键。

6. **星星上限压到 3 颗/天**。这一组是情绪出口，不该被当成任务刷。
   排行榜里「心情与关怀」记的是**连续记录天数**（score 传 streak），
   不是「攒了几颗星」——攒星星这件事本身就和它想做的事相反。

### 隐私边界（这条最要紧）

心情记录和「想对爸妈说的话」**只写本机 preferences**，不上传、不同步、不做分析上报、
不记位置和联系人。**家长面板看不到内容明细**，只能看到「记了几天」。

这不是技术限制，是产品判断：一旦孩子怀疑「我妈能看到」，往后他写的每一个字都会先想
「被看到会不会挨骂」，那还不如不写。改这块代码时请守住这一条。

### 内容红线

`CareData.cs` 的写作原则写在文件头注释里，`tools/check-care.js` 把它变成了脚本：

- 不许出现「想开点」「别想太多」「没什么大不了」「坚强一点」——
  这些话把情绪变成「你不该这样」，是二次伤害；
- 出现自伤话题的段落，必须给出真实可拨的号码；
- 求助渠道里必须有 12355，以及 110 或 120；
- 暖心话不许是命令句（「你要…」「你应该…」）。

写这类检查的价值不在「防手滑」，而在**以后改文案时不会悄悄退化**。
内容比代码更容易被随手改坏，而且改坏了不会有任何报错。

### 移植时踩到的两个坑

1. **`scale` 不能当成员名**。`BreathingPage` 里写了 `@Local scale: number`，
   报 `Property 'scale' in type 'BreathingPage' is not assignable to the same property
   in base type 'CustomComponent'` —— `scale` 是 ArkUI 通用属性。
   「六、已知限制」里早就记着这一条，写的时候还是踩了。改名 `circleScale`。
2. **`Flex` 没有 `rowGap`**。`rowGap` 是 `Grid` 的属性，`Flex` 换行后的行距只能靠
   子元素的 `margin` 撑。`Column` / `Row` 有 `space` 参数，`Flex` 没有。

另外 `CareStore` 里 `letters` 作为私有字段和 `letters()` 方法重名，
TS 直接报 `Duplicate identifier` —— 字段改名 `items`。

## 五之十、移植两个老工程：记住它 / 三三合成

十四五年前的两个 Cocos2d-x 时代工程，都不是「拷过来就能跑」的：

| 工程 | 原形态 | 为什么不能直接跑 | 移植做法 |
|---|---|---|---|
| `kidrememberit-master` | Cocos2d-x 3.x / C++，1989 行 | 引擎 API（`Sprite`、`ProgressTimer`、`EventListenerTouchOneByOne`）在鸿蒙上没有对应物；资源是 177KB 的 plist 图集 | 读 C++ 把**规则与难度模型**搬出来，界面用 DOM/CSS 重写 |
| `mr3-master` | 自定义 GL 引擎 / JS，7974 行 | `game.js` 第一行就 `require('opengl')`，`component/*`、`event/*`、`tools/*` 全不在仓库里 —— 是宿主（Native JS 运行时）注入的，源码在手也起不来 | 整条依赖链换成 DOM/CSS，**只保留决定手感的规则数值** |

### 记住它：把 2015 年的四条反思真的做进去

原工程 README 末尾自己写了一段「版本 1 测试结果」：女儿玩了不到 5 分钟就失去兴趣，
并列出两条要改的（要教程、加种类太陡）和两条想改的（融合翻牌配对、用数字代替动物）。
移植时这四条全部落地：

| 原版问题 | 这一版怎么改 |
|---|---|
| 孩子没注意到倒计时 | 顶部计时从「一条 3px 进度条」改成**条 + 大字秒数**：≤35% 变橙、≤3 秒变红并脉冲，最后 3 秒每秒滴一声（WebAudio 现场合成，不带音频文件） |
| 没有任何引导 | 首次进入自动弹 3 步教程（先记住 → 按序摆回 → 每 3 关换配对），首页也能再点「怎么玩」 |
| 加种类会陡增难度 | 起步只有 **2 种牌**；`types ≤ floor(张数/2)` 的约束照原版保留；**每两关**才动一次牌数/种类（原版每次成功都 +1 种，5 关到 9 种） |
| 单一玩法单调 | **每第 3 关**切成翻牌配对（原工程 README 的 Step 2），两种玩法交替 |
| 动物图集对初学者太难 | 牌面换成 **1~9 数字 + 固定配色**，顺带省掉 177KB 图集与 plist 解析 |

保留下来的是原版真正推敲过的东西：

- **难度因子**：张数 5~14、种类 2~9、记忆/重现时间因子 0~255。
- **时间公式**：`t = min(5n, n × (1 + 8 × (255 - f) / 255))`
  —— f=255 时每张 1 秒（最狠），f=0 时 9 秒/张被 5 秒/张封顶（最松）。
- **升降级**：`toTheNextDifficulty()` 先加种类，种类超过 `张数/2` 再加张数并把种类压回下限；
  这一版另加了「失败就把时间放宽、宽到头才减张数」的反向路径，孩子不会卡死在某一关。

### 三三合成：先把「跑不起来」这件事解决掉

`mr3` 是 Threes! 的克隆（1+2=3；3+3=6；6+6=12……1+1 和 2+2 不能合），
但它是给某个 Native 容器写的：场景、布局、触摸、GL 状态机全由宿主提供。
所以要「改成离线运行」，本质上不是改配置，而是**把这四层宿主依赖换掉**：

- `require('opengl')` → DOM 砖块 + CSS 过渡（`left/top` 120ms），不再需要 GL 上下文；
- `component/scene.js`、`event/touchnode.js` → 一块 `#board` 上的 touch/mouse/keydown；
- `tools/layout.js` → 每次 `resize` 量一次 `#stage`，按 `min(宽, 高-4, 520)` 定棋盘边长；
- 存档 `config/history.js` → `localStorage` 一个 `ks3.best`。

保留的原版数值（这些才是手感）：

- `canMerge`：1+2=3；相同且 ≥6 才能合；1+1、2+2 不行；6144 封顶（原版 `MAX_COUNT`）。
- 新块生成：基本只出 1/2/3，权重 10:10:10 且**连续同值不超过 4 次**（原版 `CellRandom.mAdjust` 的自我平衡）；
  盘面出现 48 之后 8% 概率给一块 `mx/8` 档的「台阶牌」（原版 `mOthers` 补偿分支）。

**唯一改掉的是计分**：原版用 `getBonus` 算 3 的幂（合出 12 给 27 分），孩子算不清自己怎么加的，
这里改成「合并后的值」（合出 12 就是 +12），和 Threes! 一致。分数上限和排行榜不受影响。

### 移植时踩的四个坑

1. **记忆阶段到点被判负**：三个阶段的计时器共用一个回调，最初三个分支都写「结算失败」，
   结果记忆时间一到直接弹「时间到了」。正确流程是：记忆到点 → 翻面进还原阶段，只有还原/配对到点才算输。
2. **牌堆双重绑定**：`addEventListener` 之后又设了 `onclick`，一次点击触发两遍，
   点一下放两张牌，第二张必然错 —— 孩子怎么点都过不去。现在统一走 `onclick`，删牌后整排重绑。
3. **配对关对数数不满**：第 5 关是 6 对，但种类上限只给了 4 种，同一张牌出现 4 次，
   「配掉两张还剩两张」，清完也不结算。改成 `typeMax = max(pairs, types+1)`，每种最多两张。
4. **下一块预览不刷新**：`addRandom()` 用掉 `nextValue` 却没摇新的，整局只出同一个数。
   星数是小事，「预览和实际给的牌不一致」会让大孩子一眼看出是 bug。

两个都写成了可回归的断言：`tools/test-memory.js`（46 项）、`tools/test-threes.js`（37 项），
在无头 Chrome 里跑真实页面，覆盖规则边界、出题不变量、升降级、上报参数与布局。

## 五之十一、词语组合 / 单词组合：一套判定，两种单位

两个游戏是**分开的**：独立目录（`playland/wordzh`、`playland/worden`）、独立星星 key、
独立关卡存档（`ksword.zh.best` / `ksword.en.best`）。语文用字块、英语用字母块，
混成一个游戏孩子会分不清规则；星星也分开记，家长能看到「中文字会拼、英文单词还生」。

判定规则只有三条，两边逐字相同：

| | 词语组合（语文） | 单词组合（英语） |
|---|---|---|
| 拼的单位 | 一个汉字 | 一个字母 |
| 词库 | 70 个两字词 + 48 个四字成语 | 60 个三字母 / 60 个四字母 / 35 个五字母单词 |
| 每关词数 | 4 个 | 4 个 |
| 难度推进 | 1~3 关全两字词；4~5 关混 1 个成语；6 关起 2 个成语 | 1~2 关全三字母；3~5 关混 2 个四字母；6 关起加 1 个五字母 |
| 配色 | 绿色系：墨绿草地渐变 + 米白字牌 + 深绿字 | 照概念图：白/浅灰点阵底 + 白底彩字块 + 淡蓝虚线 |

```
1. 点一块 → 接在当前串后面；
2. 当前串必须是某个「还没拼出来的词」的前缀，否则这一下不算，串不动（只抖一下）；
3. 串正好等于某个词 → 这个词消掉，加 word.length × 10 分；词清空 → 过关。
```

**第 2 条同时是脚手架**：盘面上只有「接得上」的块会响应，接不上的点了只会抖。
12 个字母里能点的其实只有一两个，孩子不用瞎试，也不会因为点错就把串弄乱。

**为什么不做拖拽连线**：孩子手指中途一抬线就断，断了只能重来。点选 + SVG 画线，
视觉上还是「连连看」，但每一步都能反悔（再点已选的块，它和它后面的一起取消）。

### 出题：牌面必须刚好够用

字块是「所有词的字全部拆开、整体打乱」，所以**每种字的块数 = 各词对该字的需求总数**。
判定只认字符不认来源，先拼哪个词都不会把后面的词卡死 —— 这条不变量写成了断言
（`tilesMatchWords`：牌面字符的多重集合 === 所有词字符的并集）。

列数按「最后一行别只剩一两个」挑，不按块大小挑：

```js
function pickCols(n) {
  var best = 4, bestRem = -1;
  for (var c = 4; c <= 5; c++) {
    var rem = n % c;
    if (rem === 0) return c;            // 正好排满
    if (rem > bestRem) { bestRem = rem; best = c; }
  }
  return best;
}
```

16 张牌排 5 列会变成 `5/5/5/1`，最后一张孤零零挂着，和「记住它」踩过的坑一模一样；
现在 16 张走 4 列（`4/4/4/4`）、14 张走 5 列（`5/5/4`）、10 张走 5 列。

### 移植时踩的四个坑

1. **星形节点压住字**：一开始把 `✦` 画在每个选中块中心往上一丁点，块只有 69vp 高，
   正好压在字上，看着像脏点。概念图里的星星是**线上的节点**，改成画在每段连线的中点。
2. **结算弹窗里的按钮隐形**：`button.ghost` 是给墨绿页面背景配的（白字 + 半透明白底），
   放进米白的结算卡片里等于白字白底。补一条 `.sheet button.ghost` 的深字色。
3. **重复字被自己吃掉**（测试钩子）：`tapLetter('一')` 找「第一个没用过的同字块」，
   但「已选中」不算「已用掉」，于是第二次又点回同一块 —— 等于取消，`一心一意` 永远拼不完。
   钩子里补 `G.picked.indexOf(i) < 0`。（真人玩不会踩：孩子会去点另一块。）
4. **断言查错了属性**：语文的字牌底色是 `linear-gradient`，`backgroundColor` 是透明的，
   `tileCream` 一直失败。渐变要查 `backgroundImage`。

`tools/test-words.js` 一次跑两个游戏两轮无头浏览器（44 + 47 项）：词库形状与去重、出题数量、
牌面不变量、前缀拒绝、取消选中、消词加分、结算上报（key / 星数）、降星、列数、方块尺寸、
重叠、溢出、配色（绿色 vs 白底彩块）。

## 五之十二、老鼠吃奶酪：一个 Qt 工程的算法搬进 H5

源工程是 `D:/Downloads/mice_eat_cheese_android-master`：Qt 5 + C++，3090 行，
里面 2100 行是作者自己写的 **LFEngine**（`EngineAPI.cpp` / `animation.cpp` / `gesture.cpp` /
`reimplemen.cpp`），真正属于游戏的只有 `map.h`（197 行）和 `game.h`（47 行）。

### 为什么不能直接跑

| 原版依赖 | 鸿蒙端 | 处理 |
|---|---|---|
| `QGraphicsScene` + `QGraphicsPixmapItem` 逐格贴图 | 没有 Qt | Canvas 2D 重画 |
| `QScriptEngine`（把 C++ 方法注册给 JS 调用） | 没有 | 不需要，逻辑本来就在 C++ 里 |
| 4 张 30×30 的 jpg（`img.qrc`） | —— | **全部弃用**，见下 |
| 右侧 4 个 `wall.jpg` 贴图当方向键 | —— | 底部十字方向键 + 滑动 |

`map.h` / `game.h` 里的东西是可以直译的，而且就是这游戏的手感所在：

```cpp
const static uint genCheese = 5;      // 5 条路径，5 块奶酪
const static uint avgMoveStep = 20;   // do{}while(rand()%20) —— 几何分布，平均 20 步
const static uint extraCheeseProb = 5;// 空地 1/5 概率额外长奶酪

```

移动规则在 `game.h::movePlayer()`，三条分支，原样保留：

```cpp
if (!canMove(...))                    return FailMove;   // 撞墙：不动，不罚
else if (c == 'm' || c == 'x') { subLife(); reset(); }   // 撞猫/陷阱：掉 1 命 + 回起点
else if (c == 'n')             { addLevel(); set(x,y); } // 吃奶酪：计数 +1
```

### 原样照搬会踩到的六个问题

1. **素材是梗图。** `mouse.jpg` 是婴儿照片，`cat.jpg` 是一张表情包脸，`cheese.jpg` 是低分辨率奶酪。
   这套东西给 6 岁小孩看很不对劲，而且 30×30 放大到 30vp 必糊。全部改成 Canvas 路径手绘：
   墙画成带顶面高光的圆角砖，猫有耳朵和鼻子，陷阱是三层同心圆加四根尖刺，老鼠有粉耳朵和尾巴。
2. **致死物密度 50%。** `genOther()` 是「非路径格有一半变成猫或陷阱」，31×31 就是 430 只，
   每格都是危险物，开局脚下四周全是猫，动一下就掉命。改成按关卡配固定只数（13×13 是 7 猫 3 陷阱）。
3. **猫会把奶酪围死。** 撞猫要掉命回起点，等于猫格不可通行；但原版随机撒猫不检查连通性，
   经常把某块奶酪封在角落，那一关永远过不去。现在每撒一只都跑一次 BFS，堵住就撤回这一只。
4. **起点可能被围。** 原版起点随机，四周可能就是猫，掉命回起点又撞，能连掉到死。
   现在起点 3×3 全挖开，2 格内绝不放危险物。
5. **31×31 手机上每格 13vp。** 改成 13 / 15 / 17 三档，整图可见。
   儿童游戏里「全局看得见奶酪在哪」比「滚动跟随」重要得多。
6. **结束只有一行红字。** `AddTextItem("You are Win", ..., RGBColor(255,0,0), 140, 400)` 就没了。
   补结算弹窗、星级、上报、关卡存档。

### 生成算法：真正的坑不在连通性，在面积

原版 `genPath()` 是「从起点做 5 条随机游走，每次靠 `rand()%20 != 0` 决定继续走」。
缩到 17×17 之后照抄，结果**每格可走面积只有 5%~10%**，剩下全是砖 —— 因为
「同一条路径不走回头路」这条限制（原版 `isRepeat`）在二维格子上很容易把自己困死：
走十来步之后四面都是自己的脚印，随机挑一个方向全被排除，`break`。

原版靠 `genOther()` 里那 25% 的空地兜底，所以看不出问题。这里把加宽改成「一圈一圈往外晕染」：

```js
function widenTo(g, N, target) {          // target = 0.42
  var want = Math.floor(N * N * target);
  while (openCount(g, N) < want) {        // 没达标就再来一圈
    var cand = [];                        // 只挑「本身是墙、但四邻有空地」的格子
    ...
    shuffle(cand);
    var take = Math.floor(cand.length * 0.38);   // 每圈只吃三成，形状才不方正
    for (var i = 0; i < take; i++) g[cand[i][1]][cand[i][0]] = OPEN;
  }
}
```

只吃「贴着已有空地」的墙，所以新开的格子一定和老区域连着，永远不会挖出孤岛。
实测 12 关的可走比例稳定在 40%~45%，而且 96% 以上在同一个连通块里。

### 另外三个小修

- **起点放中段。** 一开始起点整图随机撒，落在角落时可走区就只朝一侧长，
  另一半整片是砖，看着像地图画了一半。改成「中心 ± 1 格」。
- **起点圈避让老鼠。** 起点的白色虚线圆是为了让掉命的孩子知道该回哪，
  但老鼠站在上面时一圈白环套着老鼠，看着像「选中态」。现在只在老鼠离开起点时才画。
- **原版 `extraCheeseProb` 关掉。** 那条规则是给 31×31 准备的：215 个空地能多长 43 块，
  反正过关只要 5 块，多出来的是送分。缩到 13~17 格后空地只剩 50~110 个，
  1/5 仍会多出十几块，HUD 上的「0/4」就成了假进度 —— 现在「图上几块 = 要吃几块」。

### 难度曲线

| 关 | 地图 | 生命 | 奶酪 | 猫 | 陷阱 |
|---|---|---|---|---|---|
| 1 | 13×13 | 6 | 4 | 7 | 3 |
| 2 | 13×13 | 6 | 4 | 9 | 4 |
| 3 | 15×15 | 5 | 5 | 11 | 5 |

## 五之十三、小游戏工坊：四端共用一份 H5

家长在小游戏工坊里不写代码就能做出能玩的小游戏。编辑器是**一份单文件 H5**
（`Resources/Raw/Maker/index.html`，鸿蒙侧同步到 `resources/rawfile/maker/index.html`），
Windows / Android / Linux / 鸿蒙四端共用一个文件 —— 改判定规则只改一处，
不会出现「电脑上好玩、手机上不好玩」。

鸿蒙端只补宿主独有的三件事：

| 能力 | 实现 |
| --- | --- |
| 选图导入 | `photoAccessHelper.PhotoViewPicker` 选图 → 读字节 → `Base64Helper` → `runJavaScript('window.KS.importAsset({...})')` |
| 打开作品 | `picker.DocumentViewPicker` 选 `.json` → 字节 base64 → `KS.loadProjectBase64(b64)` |
| 导出作品 | `KS.currentProjectBase64()` 取回 → `DocumentViewPicker.save({newFileNames})` → `fs.writeSync` |

### 必须走 `KSStore` 桥，不能只靠 localStorage

`Web({ src: $rawfile('maker/index.html') })` 加载出来的 origin 是 `resource://rawfile/`。
这个 origin **不保证给 opaquestorage**，实测症状是：当场存得进去、重开就空 ——
而且**一条报错都没有**，家长只会以为「我做的游戏又没了」。

所以鸿蒙端用 `javaScriptProxy` 注入了一个 `window.KSStore`：

```ts
class MakerStoreBridge {
  get(key: string): string { return store.getString(key, ''); }
  set(key: string, value: string): void { store.setString(key, value); }
}
```

页面里的存储层是这么用的（`index.html` 第 2 节）：

```js
if (window.KSStore && typeof window.KSStore.get === 'function') {
  const v = window.KSStore.get(key);   // 优先
} else {
  localStorage.getItem(key);           // 兜底（其他三端走这条）
}
```

`methodList: ['get', 'set']` 里的名字必须与类方法名**逐字一致**，且参数/返回值只能是
基本类型 —— 传对象会静默失败。作品本身就是 JSON 字符串，正好够用。

### 返回键

走 `Index.ets` 的全局拦截（`PageId.Maker` 不在白名单里，所以 `router.back()` 回家长后台）。
页面顶栏的 `‹` 也是同一个动作 —— 不额外做「先回作品大厅」：编辑器每次改动都即时存档，
退出不会丢东西，多一层返回反而让孩子以为「退不出去」。
真正会丢东西的是没导出的作品，而它就在存档里，下次进来还在。

### 长度与体积

单张导入图上限 8 MB（`MAX_IMAGE_BYTES`），超过提示「换张小一点的」而不是硬塞 ——
原图 base64 后过 `runJavaScript` 会明显卡顿甚至 OOM。页面收到后会再压到 320px 存档，
所以真正落盘的作品通常只有几十 KB。

## 五之十四、意见反馈与问卷：一条通道，三张表单

家长页新增「意见反馈与问卷」卡片，进去一页三个标签：满意度调查 / 使用问卷 / 意见反馈。

| 文件 | 职责 |
|---|---|
| `entry/src/main/ets/core/Feedback.ets` | 组 JSON、`@kit.NetworkKit` POST、失败入 preferences 队列、补传 |
| `entry/src/main/ets/pages/FeedbackPage.ets` | 三个标签的界面（星级、分项、NPS、标签、问卷、正文） |

### 为什么先入队再发

`submit()` 的第一步是 `list.push(body)` 并落盘，第二步才是发请求。这样即使发送途中
应用被系统回收，这条也不会丢 —— 重新打开时 `aboutToAppear` 里的 `flush()` 会补发。
发送成功才从队列移除；4xx（内容不合格）直接丢弃并在页面显示服务端给的原因。

### `public` 是关键字

服务端字段叫 `public`，ArkTS 里不能当属性名，所以 `Payload` 里叫 `sharedToPublic`，
序列化后做一次 `"sharedToPublic":` → `"public":` 的替换。改字段名时这两处要一起改。

### 版本号是常量

`core/Feedback.ets` 里的 `APP_VERSION = '1.20'` 需要跟 `build-profile.json5` 手工对齐。
鸿蒙端没有像 `AppInfo.VersionString` 那样统一的运行时读取入口，与其引一堆
`bundleManager` 依赖，不如写一个常量并在这里说明「改版本时记得改它」——
它只影响反馈里「哪个版本出的问题」，写错了不影响提交。

### 返回键

`PageId.Feedback` 不在 `Index.ets` 的返回键白名单里，`router.back()` 回家长后台；
页面顶栏 `‹` 也是同一个动作。

## 六、已知限制

- **反馈页尚未在 DevEco 里编译验证**：本机没有 DevEco Studio，`Feedback.ets` /
  `FeedbackPage.ets` 只做了静态核对（API 名、组件约束、@Builder 参数不能是函数）。
  第一次打开时若报错，优先看 `Record<string, number> = {}` 这类对象字面量与
  `ChipView` 的 `@Param` / `@Event` 声明。
- **代码已在 SDK 26 下编译通过**（0 错误，6 条平台能力提示）。剩下的是运行期验证：
  拉起外部应用、切后台回来的时长补记、锁屏与加时这条链路。
- **允许的编译版本组合是「compileSdk 26 + compatibleSdk 12」**。这个组合下要注意两类坑：
  - 结构体成员名不能叫 `enabled` / `scale` / `opacity` 这类 ArkUI 通用属性名，否则报
    「not assignable to the same property in base type」；
  - shape 的 `fill()` 在 SDK 26 的声明里标了 `@since 26`，为兼容 API 12 设备，
    圆形一律用 `width('100%') + aspectRatio(1) + borderRadius('50%')` 的容器实现。
- **安全区是手算的，不靠系统默认值**。沉浸式（`setWindowLayoutFullScreen(true)` + 隐藏状态栏）
  之后 ArkUI 的默认安全区只剩 `TYPE_SYSTEM`，状态栏隐藏后其高度为 0，摄像头挖孔
  （`TYPE_CUTOUT`）不参与布局，页面第一行会被挖孔压住。所以 `Kiosk.refreshSafeArea()`
  显式读取 `TYPE_CUTOUT` / `TYPE_SYSTEM` 的避让区，换算成 vp 存进 `safeTopVp` /
  `safeBottomVp`，各页面把它加进顶部内边距。**新加页面别忘了这一项**，否则真机会被挖孔挡字。
- **拉起应用只能靠显式 Want，入口类名是硬编码的**。实测 `aa start -b <包> -A action.system.home
  -e entity.system.home` 在 HarmonyOS 上返回 10103101「找不到匹配的应用」，而显式
  `-a <包>.MainAbility` 立即成功——系统不允许普通应用用 home 语义去猜入口。所以
  `AppLauncher` 按 `已知 abilityName → MainAbility → <包名>.MainAbility → EntryAbility
  → <包名>.EntryAbility → 隐式 home` 的顺序逐个试，全部失败才报错。
  预设里的 abilityName 是在模拟器上 `bm dump -n <包>` 读出来的实测值；
  相机 / 计算器 / 备忘录 模拟器没有，留空交给候选表。
- **不做包名预校验**。`bundleManager.getApplicationInfo` 在 API 26 已移除，替代的
  `getBundleInfo` 需要 API 14+ 且要申请 `GET_BUNDLE_INFO` 权限。为不抬高最低系统版本，
  添加应用时不校验包名，能否打开以孩子实际点击为准（打不开会在桌面弹提示）。
- **预设包名可能不准**。`com.huawei.hmos.*` 是常见华为系统应用的包名，随系统版本可能变化，
  以设备实测为准。
- **TTS 只有中文、只有「聆小珊」一个音色**，单次上限 10000 字符（已按 600 字切段）。
- **护眼滤镜是覆盖层**，不是真正的屏幕色温调节。鸿蒙没有给第三方应用调节屏幕色温的
  接口，`brightnessctl` 那种做法在鸿蒙上不存在。
- 家长密码是 4 位数字，安全性定位于「防孩子」而非「防拿到设备的人」，与其它端一致。
- **ArkWeb 与 Chrome 的渲染差异是实打实存在的**，目前确认一条：`border-radius` + `overflow:hidden`
  的圆角裁剪在里面装文字时不可靠（卡片数字整块丢失、还会留下斜线伪影）。
  凡是「真机才复现、Chrome 上好好的」样式问题，先怀疑这类合成/裁剪相关的差异，
  再去查逻辑 —— 逻辑在两边跑的是同一个 V8。
- **关怀中心有三处只能真机验**：
  - `ohos.want.action.dial` 拉起系统拨号盘的实际表现（模拟器上没有电话应用，
    `startAbility` 会失败，页面会给出「请手动拨打 12355」的兜底提示）；
  - 呼吸圆圈的 `animation({ duration })` 在低端机上的掉帧情况 —— 每段 4/7/8 秒，
    如果动画先跑完而倒计时还在走，视觉上会「圆先停住」；
  - `TextArea` 的中文输入法选词：输入法组词过程中 `onChange` 会带拼音上来，
    如果选词结束后光标跳到末尾，是受控写法（`text: this.draft`）的已知副作用，
    改成 `$$this.draft` 双向绑定可以规避。
